# Product Delivery Shared Context

本文件是 `product-delivery` 分组的共享上下文入口，用于让 Agent 在调用任一子 Skill 前理解整套系统的共同目标、顺序和门禁。具体执行规则仍以各子目录中的 `SKILL.md` 为准。

## 共同目标

即使用户只提供质量较差、信息不完整的 Prompt，也要通过主动发现和可观察验收，把它推进为用户价值明确、视觉干净简洁、交互完整、前后端打通且有测试证据的产品。

## 总编排关系

`deliver-product-end-to-end` 是唯一总入口，其他 Skill 是可独立验收的阶段能力：

1. `design-product-experience` 明确应用场景、目标人群、核心问题、用户旅程、信息架构和交互状态。
2. `research-product-references` 调研竞品与开源项目，输出借鉴点、复用边界和许可证判断。
3. `design-product-identity` 设计贴合主题、清新简洁的 Logo、颜色、字体与品牌变体。
4. 使用结构化 Figma 原型承载页面视觉与完整交互，并等待用户审核。
5. 用户确认原型后，`define-service-contracts` 冻结前后端契约。
6. `implement-product-frontend`、`bootstrap-backend-foundation` 和 `implement-backend-slices` 在隔离 worker 中按批准范围实现。
7. `integrate-and-verify-product` 汇总真实运行、视觉、交互、接口、安全和端到端证据。

## 双 Chat 边界

- 孵化任务保持 `DISCUSS`，只讨论做什么项目、为谁解决什么问题和 MVP 边界。
- 用户明确说“现在去把这个项目落地”或要求新开 Chat 时，进入 `HANDOFF`，生成不含敏感信息的 Project Launch Brief。
- 使用新建任务能力创建干净的执行任务，不 fork 全部聊天历史；当前孵化任务不得偷偷开始实现。
- 执行任务显式使用 `deliver-product-end-to-end` 的 `EXECUTE` 模式，不重复询问已确认事实，并继续遵守全部审批门。
- 同一项目只保留一个主执行任务；再次落地时优先继续原执行任务。

## 强制审批门

- 产品问题、目标用户和成功标准不明确时，必须主动向用户提问。
- Figma 原型和关键交互未获用户确认时，不得进入正式前后端实现。
- 原型确认不等于技术方案确认；技术选型、服务契约和实施范围需要单独冻结。
- 前后端完成不等于交付完成；必须经过真实集成、负向路径和用户体验验收。
- commit、push、PR、合并、发布和部署分别遵守当前仓库与用户的授权边界。

## 产品与体验基线

- 每项功能都要回答：为谁服务、解决什么问题、为什么现在需要、成功如何被观察。
- 页面保持清新、干净、简洁，元素紧贴主题，不用无意义装饰填满界面。
- 首次成功、高频任务、加载、空、错误、权限、恢复和反馈状态都必须设计。
- 1:1 不只指静态像素，还包括响应式、状态、动效、反馈、键盘与无障碍行为。
- 可借鉴高质量项目，但直接复用前必须验证许可证、维护状态、安全性和适配成本。

## Graph Engineering 约定

- 用状态图记录需求、决策、验收项、Issue、worker 和证据之间的关系。
- 并发数量由电脑资源和任务独立性决定，不把“无限窗口”当作目标。
- 一个可写范围只允许一个 owner；独立 reviewer 根据验收项和证据判定结果。
- 阶段失败时从最近的稳定检查点恢复，禁止跳过审批门或伪造完成状态。

## 安装与发现

`product-delivery` 只是分组容器，不应把本目录本身识别为 Skill。每个直接子目录才是独立 Skill，安装时复制到 `~/.codex/skills/<skill-name>/`，并确保其根目录直接包含 `SKILL.md`。
