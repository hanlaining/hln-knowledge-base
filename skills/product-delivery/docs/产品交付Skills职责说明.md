# 产品交付 Skills 职责说明

## 一句话说明

这一组 Skill 的目标是：把用户一句很模糊的产品想法，逐步变成经过用户审核的 Figma 原型，再完成前端、后端和测试交付。

## 分组公共文件

| 内容 | 作用 |
|---|---|
| `README.md` | 给人看的总入口，介绍整套流程、Skill 地图和安装方式。 |
| `CONTEXT.md` | 给 Agent 看的共同规则，保证多个 Skill 理解前后关系、审批门和共享目标。 |
| `docs/从烂Prompt到全栈产品交付_Meta-Skill方案V0.3.md` | 完整架构方案，说明整个自动化产品流水线如何运作。 |
| `docs/端到端产品交付Skill_验收SOP.md` | 说明如何验收这些 Skill 是否真的有效。 |

## 九个 Skill 分别负责什么

### 1. `deliver-product-end-to-end`

定位：总导演和 Meta-Skill。

用户只需要把想法告诉它，它负责：

- 判断当前处于需求、设计、开发还是测试阶段。
- 主动询问应用场景、目标用户、核心问题等信息。
- 调用其他阶段 Skill。
- 记录需求、决策、审批和验收证据。
- 控制多个 Claude CLI 或 Codex worker 并行工作。
- 在关键节点暂停并请求用户确认。

核心产物：完整交付状态、阶段决策、任务关系图和验收证据索引。

### 2. `design-product-experience`

定位：产品经理和交互设计师。

负责：

- 判断产品真正解决什么问题。
- 梳理目标用户、使用场景和核心任务。
- 设计信息架构、用户旅程和页面流程。
- 处理加载、空、错误、权限和恢复等交互状态。
- 确保产品不只是功能可用，还要体验顺畅。

核心产物：可以进入 Figma 的完整产品体验方案、页面决策和交互状态契约。

### 3. `design-product-identity`

定位：品牌与 Logo 设计师。

负责：

- 根据产品主题生成 Logo 概念。
- 设计图形标志、文字标志和组合形式。
- 输出亮色、暗色、单色、favicon 和 App Icon 等变体。
- 确定颜色、字体和品牌规范。
- 保持小清新、干净、简洁且紧贴主题的风格。

核心产物：Logo、品牌变体、色彩与字体规范以及可验证的矢量资产。

### 4. `research-product-references`

定位：竞品和开源项目研究员。

负责：

- 搜索同类产品。
- 寻找高质量 GitHub 开源项目。
- 分析值得借鉴的页面结构和交互方式。
- 判断代码能否直接复用。
- 检查许可证、维护状态、安全性和适配成本。

它不会看到项目就直接复制，而是明确区分设计借鉴和代码复用。

核心产物：竞品与开源参考清单、可借鉴点、复用边界和许可证判断。

### 5. `implement-product-frontend`

定位：前端实现负责人。

只有用户确认 Figma 原型后才启动。

负责：

- 将 Figma 页面按 1:1 视觉还原。
- 实现按钮、弹窗、表单、动效和页面跳转。
- 实现加载、空、错误和成功等真实状态。
- 处理响应式、无障碍和键盘操作。
- 复用项目已有组件库与设计 Token。

Element Plus、Iconfont 等具体方案在技术方案确认后接入，不会在产品原型阶段提前锁死。

核心产物：与批准原型视觉和交互平齐的生产前端，以及视觉与交互验收证据。

### 6. `define-service-contracts`

定位：前后端接口协议负责人。

负责在开发前明确：

- API 地址和请求方式。
- 请求与响应字段。
- 数据模型。
- 参数校验。
- 错误码和错误提示。
- 登录、认证和权限规则。
- 分页、状态机和幂等行为。

它的作用是避免前端和后端各自实现，最终无法打通。

核心产物：冻结的接口、数据模型、认证、错误和兼容性契约。

### 7. `bootstrap-backend-foundation`

定位：后端底座负责人。

负责建立生产化后端基础：

- 项目结构。
- 数据库连接和迁移。
- 配置管理。
- 日志、错误处理和健康检查。
- 认证、权限和安全基础。
- 测试框架。
- 本地启动方式。

它解决的是后端工程由谁搭建并独立验证的问题。

核心产物：可真实启动、可测试、可扩展的后端基础工程和底座证据。

### 8. `implement-backend-slices`

定位：后端业务开发负责人。

后端底座建立后，它按照业务切片开发：

- 一个 Issue 对应一个可独立验收的业务能力。
- 严格遵守已经冻结的接口契约。
- 编写数据库、领域逻辑、API 和测试。
- 每个切片独立开发、独立审核。
- 在电脑资源允许时使用多个 worker 并行实现。

例如登录、用户资料和账单记录可以分别作为独立切片。

核心产物：满足冻结契约并具有独立测试证据的后端业务切片。

### 9. `integrate-and-verify-product`

定位：最终集成和测试负责人。

负责把前端和后端真正连接起来，并验证：

- 项目能否真实启动。
- 数据库是否正常。
- 接口契约是否一致。
- 页面视觉和交互是否符合 Figma。
- 登录、权限和异常路径是否正确。
- 首次使用、高频任务和失败恢复是否顺畅。
- 安全、无障碍和端到端测试是否通过。

最终提供的不是一句“测试通过”，而是一套可以检查的验收证据。

核心产物：完整候选产品、端到端测试结果、视觉与体验证据和最终验收报告。

## 完整调用顺序

```text
用户的模糊想法
  ↓
总编排 Skill 主动提问
  ↓
产品价值和用户体验设计
  ↓
竞品与开源项目研究
  ↓
Logo、品牌、页面与交互设计
  ↓
生成 Figma 原型
  ↓
用户审核并确认
  ↓
技术方案与前后端契约
  ↓
前端、后端并行开发
  ↓
真实集成与自动化测试
  ↓
用户最终验收
```

## 双 Chat 工作方式

推荐把项目孵化和项目执行分开：

```text
孵化 Chat：轻松讨论做什么项目
  ↓
用户确认项目，并说“现在去把这个项目落地”
  ↓
HANDOFF：整理 Project Launch Brief
  ↓
新建执行 Chat：使用 EXECUTE 模式完成全部交付流程
```

孵化 Chat 不创建工程、不调用 Figma、不写业务代码。交接包只保留用户确认事实、明确推断、Rxx/ACxx、MVP、体验方向、约束、审批状态和待决问题，不复制冗长聊天或任何账号凭据。

执行 Chat 不会重新询问已经确认的问题，而是从证据支持的最远状态继续；Figma、技术方案、Git、账号、付费、生产和部署仍分别遵守审批门。如果新任务创建失败，孵化 Chat 只输出可复制的执行 Prompt，不会自行转为执行。

## Figma 与自建 Skill 的关系

当前这九个 Skill 是自建的产品交付控制层。Figma 创建、Figma 读取和 Figma 1:1 实现会调用已有的官方或成熟 Figma Skills，不在知识库里重复复制第三方源码。

Figma 原型是正式开发前的强制审核门：用户没有确认页面视觉与关键交互之前，不进入正式前端和后端实现。原型确认后，再讨论并冻结 Element Plus、Iconfont、后端框架、数据库等具体技术方案。

## 验收要点

验收这套 Skill 时，至少确认：

1. 面对模糊 Prompt 时会主动询问用户、场景、问题和成功标准。
2. 产品设计同时覆盖用户价值、页面结构、交互状态和失败恢复。
3. Logo 与页面视觉符合清新、干净、简洁且贴合主题的要求。
4. Figma 原型未经用户确认时不会提前进入开发。
5. 前端实现同时对齐视觉、交互、响应式和真实状态。
6. 后端底座、服务契约和业务切片都有明确 owner 与验证证据。
7. 多 worker 并发受电脑资源和写入范围约束，不以无限窗口为目标。
8. 最终交付经过真实启动、前后端集成、负向路径和端到端验收。
