# 从模糊需求到多 CLI 执行：Agent 产品规划与交付 SOP

> 案例来源：Finance Agent 从概念讨论、Codex CLI 选型、三角色 Skills、桌面客户端、任务拆分到墨刀 UI 验收的完整过程
> 适用对象：产品经理、技术负责人、AI 项目负责人、Codex 主监工、Claude Code CLI 执行人员
> 目标：把一句模糊的 Agent 想法，转成能开发、能监督、能 Review、能截图、能验收的 MVP

> **本 SOP 的核心打法：全过程只盯两个东西——用户写的需求描述，以及用来验收最终产品形态的测试用例。计划、架构、任务 MD、代码和 PR 都是中间产物，不是判定产品对错的最终依据。**

## 0. 双锚点打法：需求描述 + 验收测试

这套方法中有且只有两个核心锚点。

### 锚点 1：用户的需求描述

- 由用户描述自己想做什么、给谁用、最终希望看到什么。
- AI 负责整理、复述、暴露歧义和给出计划，但不能擅自改写用户意图。
- 当 AI 给出的产品形态有偏差时，用户通过反问、删减或重新定义来继续引导。
- 每次纠偏都要回写到需求描述，不能只留在聊天记忆里。

### 锚点 2：定义产品形态的验收测试用例

- 测试用例回答“产品做完后，我实际怎么操作、看到什么、什么才算通过”。
- 这里的“测试”不只是单元测试，还包括页面形态、用户路径、权限弹窗、真实数据输入、输出格式和真实客户端截图。
- 验收用例是对产品形态的可执行描述，应在大规模开发前写出。
- 需求调整后，必须同步修改对应测试用例；用例没有变，产品的通过标准就没有变。

两个锚点之间的闭环：

~~~text
用户写需求描述
→ AI复述产品形态并给出计划
→ 把产品形态写成验收测试用例
→ 拆任务、实现、集成
→ 按测试用例验收真实产品
→ 发现偏差
→ 用户继续引导
→ 更新需求描述和对应用例
→ 再进入下一轮
~~~

因此，主监工在任何时刻都应能回答：

1. 当前实现对应用户的哪条需求。
2. 完成后用哪条测试用例验收。

如果一项工作既找不到对应需求，也找不到验收用例，就不应继续做。

### 0.1 已封装为可复用 Skill

本 SOP 的核心打法已封装为：

~~~text
$requirement-acceptance-planner
~~~

默认安装位置：

~~~text
~/.codex/skills/requirement-acceptance-planner/
~~~

新的 Chat 中可直接使用：

~~~text
使用 $requirement-acceptance-planner 把我的产品想法整理成需求 Rxx、
验收用例 ACxx 和可执行的任务计划。
~~~

当用户纠偏时：

~~~text
使用 $requirement-acceptance-planner 处理我这次纠偏，
告诉我哪些 Rxx、ACxx、Txx 需要改，哪些仍然有效。
~~~

当需要多 CLI 执行计划时：

~~~text
使用 $requirement-acceptance-planner 把已确认的 Rxx 和 ACxx
拆成任务 MD、依赖图和最多三个 CLI 的分波执行计划。
~~~

拷贝整个 `requirement-acceptance-planner` 目录到其他人的 `~/.codex/skills/` 后即可复用。

### 0.2 从 Prompt 驱动转向 Skill 驱动

> 参考观点：LovCooper 中 yangyida 的《Skill过多怎么怎么提高命中率》。该文章提出：支持 Skills 的 Agent 会先看 Skill 的名称和描述，再决定是否加载完整内容；所以不应只不断优化一条长 Prompt，而应提高 Skill 描述的区分度、建立分层路由、补充负面边界，并使用召回和重排。

#### 核心结论

在现在的 AI 协作方式中，Prompt 仍然有用，但不再应该承载全部稳定流程。

用户不应每次都重写一条超长 Prompt，反复告诉 AI：

- 你是谁。
- 要按哪些步骤做。
- 要读哪些资料。
- 哪些情况不能做。
- 最后怎么检查。

这些稳定、可复用、会重复出现的内容，应该沉淀为 Skill。Prompt 只保留本次任务的变量：

~~~text
我现在要解决什么
输入资料是什么
本次有什么特殊约束
~~~

因此，这套打法不是“不要 Prompt”，而是：

> **Prompt 负责表达当前意图，Skill 负责稳定执行方法，用户的需求和验收用例负责判定方向与结果。**

双锚点仍然不变：

- `Rxx` 需求描述决定“要做什么”。
- `ACxx` 验收用例决定“什么算做对”。
- Skill 只是 AI 从 Rxx 走到 ACxx 的可复用执行轨道，不是第三个产品事实源。

#### 新的 AI 使用分层

~~~text
用户需求 Rxx + 验收用例 ACxx
                    ↓
Prompt：只描述本次任务和变量
                    ↓
Skill Router：判断本次应该用哪个 Skill
                    ↓
Domain Skill：加载稳定流程、边界、模板和检查项
                    ↓
Tool / Codex CLI：读取、分析、修改、运行和请求授权
                    ↓
真实证据：回到 ACxx 验收
~~~

用户主要维护的是需求和验收，不是记住一百个 Skill 的名称。AI 应该根据当前任务自己对标、自己选择最合适的 Skill。

#### 为什么不应继续主要盯 Prompt

| 问题 | 只靠 Prompt 的后果 | 改成 Skill 后 |
|---|---|---|
| 流程稳定性 | 每个人的写法不同，容易漏步骤 | 统一流程和门禁 |
| 上下文成本 | 每次都重复输入大段内容 | 命中后才加载必要内容 |
| 团队共享 | Prompt 散落在个人聊天中 | Skill 可以进 Git、Review和版本化 |
| 质量验证 | 很难知道哪个句子造成偏差 | 可对路由和执行分别写测试 |
| 错误纠正 | 继续把 Prompt 写得更长 | 修正 Skill 描述、负面边界或流程 |

Prompt 越长不等于系统越可靠。如果同一类要求已经反复出现两到三次，就应评估是否将它升级为 Skill。

#### 结合 yangyida 文章的四个路由原则

##### 1. 提高 Skill 描述的区分度

Skill 的描述不能只写“用于分析”或“用于开发”，必须写清：

- 它解决什么。
- 用户说哪些话时应该触发。
- 它产出什么。
- 哪些相似任务不属于它。

错误描述：

~~~text
用于产品规划。
~~~

正确描述：

~~~text
当用户给出模糊、口语化或反复纠偏的产品想法，
需要生成 MVP 产品形态、Rxx 需求、ACxx 验收用例、
Txx 任务和多 CLI 执行计划时使用。
不用于直接修复已定位的单个代码 Bug。
~~~

##### 2. 使用 Skill Tree 分层路由

不要把一百个 Skill 全部平铺给 AI。先按任务大类分层：

~~~text
L0 任务域
├─ 产品与需求
├─ 软件开发
├─ UI 与设计
├─ 数据与文档
├─ 安全与审计
└─ 发布与运维

L1 领域 Skill
产品与需求
├─ requirement-acceptance-planner
├─ user-research
└─ product-review

L2 任务变体
requirement-acceptance-planner
├─ 首次规划
├─ 用户纠偏
├─ 任务 MD 拆分
└─ 多 CLI 监工
~~~

路由层只做分类和候选选择，不复制下层 Skill 的完整内容。

##### 3. 同时写清“什么时候不能用”

只写正面触发词，多个 Skill 很容易一起命中。每个 Skill 必须有负面边界：

| Skill | 应该使用 | 不应该使用 |
|---|---|---|
| 需求验收规划 | 产品想法、MVP、验收用例、任务拆分 | 单一已定位 Bug 的直接修复 |
| UI 实现 | 有明确设计稿并需要写页面 | 只需评审产品方向 |
| 发布 | 用户明确要求发版或部署 | 只要求本地构建或查看状态 |

负面描述的价值不是限制 AI 能力，而是减少误召回和越权动作。

##### 4. 先召回候选，再重排

不要让 AI 一次读完一百个 Skill 正文。应该：

~~~text
用户输入
→ 根据名称、描述、任务域和关键词召回 Top K 候选
→ 用“应该用 / 不应该用”边界排除误命中
→ 比较剩余候选与当前任务的匹配度
→ 选择 1 个主 Skill，必要时增加少量辅助 Skill
→ 只加载命中 Skill 的完整内容
~~~

`K` 不应写死为 10，小型池可以只召回 3 个，大型池可以召回 5–10 个。核心是不加载与当前任务无关的完整 Skill。

#### Prompt 升级为 Skill 的标准 SOP

| 阶段 | 动作 | 产物 | 闸门 |
|---|---|---|---|
| P0 采集 | 找出反复出现的 Prompt、纠偏和检查要求 | 原始对话样本 | 同类流程确实重复出现 |
| P1 抽取 | 把稳定步骤、边界和验收从 Prompt 中抽出 | Skill 流程草案 | 不包含单次任务的临时变量 |
| P2 定义 | 写清名称、做什么、何时用、何时不用 | Skill metadata | 能与相似 Skill 明确区分 |
| P3 分层 | 把 Skill 放入对应的任务域和 Skill Tree | 路由索引 | 不在大池中无差别平铺 |
| P4 召回 | 根据 metadata 选出 Top K 候选 | 候选集 | 正确 Skill 必须在候选内 |
| P5 重排 | 使用正向触发和负面边界选主 Skill | 本次 Skill 计划 | 不应命中的 Skill 被排除 |
| P6 执行 | 加载命中 Skill 正文、references 和脚本 | 可复现执行过程 | 不因换 Chat 或换人而改变主要步骤 |
| P7 验收 | 用 ACxx 和真实证据验收 | 命中与结果报告 | 不以“Skill 已运行”代替结果正确 |
| P8 改进 | 记录误命中、漏命中和用户纠偏 | 路由测试集 | 优先修路由和 Skill，不是继续加长用户 Prompt |

#### Skill 路由必须有独立测试用例

Skill 本身有两类验收：

1. **路由是否正确**：应该命中的任务能否选中，不应命中的任务能否排除。
2. **执行是否正确**：命中 Skill 后，最终产品是否通过 ACxx。

路由用例示例：

| 用户输入 | 期望主 Skill | 不应命中 |
|---|---|---|
| “我有一个模糊的银行 Agent 想法，帮我收敛 MVP” | requirement-acceptance-planner | 发布、UI 实现 |
| “你理解偏了，新建 Chat 不应该强制选角色” | requirement-acceptance-planner 的纠偏模式 | 新建一套完整计划 |
| “按已确认的 Figma 实现这个页面” | UI 实现 Skill | 产品需求收敛 |
| “查看这个 PR 有没有中高风险” | 代码风险门禁 Skill | 发布 Skill |
| “只是解释这段代码，不要修改” | 代码阅读/解释 | 实现和交付 Skill |

需要持续统计：

- 正确命中率。
- 误命中率。
- 漏命中率。
- 用户需要手动指定 Skill 的比例。
- 平均 Prompt 长度是否下降。
- 命中 Skill 后 ACxx 的通过率。

#### 放到 Finance Agent 中的实际形态

Finance Agent 不应要求银行员工理解 Skill 的技术名称。

~~~text
通用 Chat
→ 用户直接描述业务问题
→ 路由器在“银行强制池 + 共享池”中选择 Skill
→ 执行后展示引用、计算和待确认项

专家中心
→ 用户主动选一个专家
→ 专家只改变推荐 Skill 候选池和输出结构
→ 路由器仍根据本次任务自动选择具体 Skill
~~~

必须保持三条边界：

1. 角色不与员工岗位绑定。
2. Skill 不扩大文件、网络或 Tool 权限。
3. 路由命中不等于结果正确，最终仍由 ACxx 和真实证据验收。

#### 这套方法最终减轻的是什么

用户以后不需要：

- 每次都写超长 Prompt。
- 反复说明同一套步骤。
- 记住每个 Skill 的技术名称。
- 亲自决定哪个 Skill 最匹配。
- 因为 AI 选错方法而从头纠正整个过程。

用户仍然只需要盯住：

1. 我的需求描述对不对。
2. 用来验收产品形态的测试用例对不对。

其余的“选方法”和“走流程”，应由 AI 通过 Skills 自动完成。

## 1. 这套 SOP 解决什么问题

很多 Agent 项目一开始只有一句话：

> 我想做一个面向金融机构的 Agent，使用 Codex CLI，带角色、Skills 和 Tools，还要做成桌面客户端。

这句话不能直接开发，因为其中混合了至少六类问题：

- 产品最终是什么样。
- 用户从哪里进入、最后得到什么。
- 哪些能力复用，哪些界面自己做。
- 哪些功能是 MVP，哪些以后再做。
- 谁来开发，怎么拆任务，怎么避免多人冲突。
- 最后看什么证据才算完成。

本 SOP 的目标不是教人写一份“看起来很完整”的大方案，而是形成下面这个闭环：

~~~text
原始需求
→ 需求编号
→ 产品形态
→ MVP边界
→ 验收测试用例
→ 技术路线
→ 复用边界
→ 仓库基线
→ 总体计划
→ 小任务MD
→ 多CLI执行
→ PR与集成
→ 真实运行
→ 按用例截图与验收
~~~

## 2. 本案例最后收敛成什么

经过多轮讨论，Finance Agent 最终收敛为：

- 产品形态：Electron C/S 桌面客户端。
- Agent 内核：Codex CLI 的 `codex app-server`。
- 不是：Codex 官方桌面客户端套壳。
- 不是：自研第二套 Agent Runtime。
- 不是：ACP 中转方案。
- 默认入口：通用 Chat。
- 独立入口：专家中心。
- MVP 专家：制度资料问答、企业经营数据分析、授信材料预审。
- 核心能力：Role、Skill、Tool。
- 模型访问：国内 Model Gateway，真实上游 Key 不进入客户端。
- 本地能力：读取用户授权目录，使用 Codex 原生沙盒和审批。
- 首阶段：Mac 开发和验收。
- 后续阶段：Windows 安装包与真实目录越界测试。
- UI 目标：墨刀《银行智能 Agent｜Codex 清新版》。
- 开发组织：一个 Codex 主监工，最多两个或三个本地 Claude Code CLI。

这就是需求收敛后的“产品结论”。在得到这个结论前，不应进入大规模编码。

## 3. 本次讨论的关键转折

### 3.1 从“大而全方案”转为只看两头

用户明确提出：

> 我只要 1 和 100 的两头。告诉我做成什么样，最终用户得到什么。中间黑盒不需要展开。

这是本次最重要的纠偏。

错误表达：

~~~text
Service A
→ Adapter B
→ Gateway C
→ Runtime D
→ Protocol E
~~~

正确表达：

~~~text
用户看到什么
→ 用户怎么操作
→ 系统最终返回什么

底层复用了什么
→ Codex CLI提供哪些能力
→ 哪些外部项目只借鉴UI或方法
~~~

产品评审优先需要的是：

1. 这个东西最后长什么样。
2. 用户为什么愿意使用。
3. 使用后得到什么结果。
4. 底层能力来自哪里。
5. 什么结果算成功。

详细类名、Service 名和协议字段应放到开发任务，不应占据产品方案主体。

### 3.2 从“新建 Chat 先选角色”改为通用 Chat 默认进入

初期容易把角色设计成强制入口：

~~~text
新建任务
→ 先选专家
→ 再进入Chat
~~~

实际产品决策改为：

~~~text
新建Chat
→ 默认通用助手

专家中心
→ 用户主动选择角色
→ 创建独立专家Chat
~~~

这样做的好处：

- 用户学习成本更低。
- 不把角色与员工岗位绑定。
- 不阻塞普通问题。
- 专家角色只是方法、Skill 和呈现方式，不增加权限。

### 3.3 从“客户端等于不需要沙盒”改为客户端仍需权限边界

桌面客户端可以访问本地能力，但这不代表应该获得整台电脑权限。

最终规则：

- 用户选择资料目录。
- 该目录成为当前任务工作区。
- Codex 使用 `workspace-write`。
- 越界或高风险动作使用 `on-request`。
- 角色和 Skill 不扩大目录权限。
- “信任任务”不能等价于关闭沙盒。

结论：客户端解决的是“本地能力入口”，沙盒解决的是“能力边界”，二者不能互相替代。

### 3.4 从“直接套 Codex 页面”改为自己做 Agent 页面

最终选择：

~~~text
自己设计Electron客户端
→ Electron主进程启动Codex CLI
→ 使用codex app-server通信
~~~

不采用：

- 直接套官方 Codex 桌面客户端页面。
- 让用户自己安装 Codex CLI。
- 页面暴露终端、Provider、Base URL 和 Key。

这里需要区分：

- 开发员工：Claude Code CLI。
- 产品 Agent 内核：Codex CLI。
- 用户界面：Finance Agent 自己的 Electron 页面。

### 3.5 从“联网就是一个开关”改为区分两种联网

联网至少有两条链：

~~~text
模型联网：
客户端 → Codex App Server → Model Gateway → 模型

工具联网：
Codex执行的命令、Web Search、GitHub、天气API等
~~~

推荐默认：

- 模型网关允许访问。
- Agent 命令联网默认关闭。
- 银行专家默认只读指定资料。
- 需要监管查询时启用可信搜索 Skill 和域名白名单。
- 天气、GitHub 等通用能力放在通用助手或独立 Tool。

### 3.6 从“有 PR 就是完成”改为区分四个完成层级

必须区分：

1. 代码写在某个分支。
2. 代码已经形成 PR。
3. PR 已经集成到同一基线并真实运行。
4. 用户完成端到端验收。

本案例曾出现十个 Open PR，但 `main` 仍只有初始化文件。这说明：

> PR 数量不能代表产品完成度。

真正的 MVP 完成必须有统一集成、真实运行、截图和验收证据。

## 4. 标准流程总览

下表的每个阶段都是中间过程。阶段产物必须同时回指需求编号（Rxx）和验收用例编号（ACxx），防止计划和实现逐渐偏离用户意图。

| 阶段 | 核心问题 | 输出 | 闸门 |
|---|---|---|---|
| S0 原始需求 | 用户到底想做什么 | 原始需求记录 | 不急着定技术 |
| S1 产品收敛 | 用户最终得到什么 | 一句话产品定义、草图 | 用户确认产品形态 |
| S2 MVP 边界 | 第一阶段只证明什么 | In/Out Scope | 不再无限加功能 |
| S3 技术路线 | 复用什么、自己做什么 | 架构结论 | 技术 PoC 可验证 |
| S4 可信与权限 | 数据、Key、网络、文件怎么控 | 安全边界 | 不以 UI 假权限代替真实限制 |
| S5 仓库基线 | 在哪里开发 | repo/branch/worktree | 路径、Git 授权明确 |
| S6 总体计划 | 全局怎么落地 | 总体实施计划 MD | 编号和依赖统一 |
| S7 任务拆分 | 谁做哪一小块 | Txx/UIxx 任务 MD | 每张任务可独立验收 |
| S8 多 CLI 调度 | 如何监督执行 | 主监工 Prompt、状态看板 | 并发和文件范围受控 |
| S9 PR 集成 | 如何进入 main | PR 顺序、冲突处理 | 测试与风险清零 |
| S10 UI 验收 | 页面是否真一致 | 真实窗口 PNG、差异表 | 不是 AI 效果图 |
| S11 最终验收 | 产品能否交付 | 验收报告 | 用户可自行复验 |

## 5. S0：记录原始需求，不急着翻译成技术

### 输入

用户的口语化表达，例如：

> 做一个面向金融机构的数据分析 Agent，复用 Codex CLI，有角色和 Skills，用户不用翻墙，也不需要自己填 Key。

### 操作

先原样记录，不立刻补全用户没说过的内容。

把需求拆成四类：

- 明确要求。
- 推测要求。
- 未知项。
- 冲突项。

### 输出模板

~~~text
明确要求：
- R01：

推测但未确认：
- （待补充）

当前未知：
- （待补充）

存在冲突：
- （待补充）

用户已确认的产品形态：
- （待补充）
~~~

### 常见错误

- 用户说轻量 Agent，却直接设计微服务矩阵。
- 用户说第一步看 Agent + Skill，却加入 PPT、OCR、支付和多模型。
- 用户要产品结果，却只解释协议和 Adapter。

## 6. S1：使用“五点论”收敛产品

所有 Agent 产品需求先回答五个问题。

### 第一点：做成什么

必须是一句话产品定义：

> 一个面向金融机构的 Electron 桌面 Agent，用户通过通用 Chat 或专家中心调用 Codex CLI 能力，对授权资料进行可信问答和分析。

### 第二点：用户怎么用

描述最短旅程：

~~~text
安装客户端
→ 登录
→ 新建通用Chat或进入专家中心
→ 选择资料目录
→ 输入问题
→ 查看带来源和待确认项的回答
~~~

### 第三点：复用什么

必须把复用分成三类：

| 类型 | 含义 | 案例 |
|---|---|---|
| 直接复用 | 使用对方现成运行能力 | Codex CLI/App Server |
| 选择性抽取 | 复用部分代码并调整 | Electron 外壳、Chat 状态、文件选择 |
| 只借鉴 | 参考产品结构或方法，不复制 Runtime | WorkBuddy 角色中心、Gundam/PCB 状态展示 |

### 第四点：第一阶段不做什么

Out of Scope 必须写清楚，例如：

- PPT。
- OCR。
- 完整 Excel。
- 支付和充值。
- 多模型市场。
- 银行核心系统。
- 真实授信决策。
- Windows 安装包，若当前只做 Mac。

### 第五点：怎么验收

必须是用户可操作、可观察的结果：

- 客户端能启动。
- 通用 Chat 能工作。
- 三个角色可以主动选择。
- 三个 Skills 输出效果不同。
- 回答有来源和待确认项。
- 用户不填真实 Key。
- 未授权目录不能读取。
- 流式、停止和追问可用。

这些结果不能只停留在一句“验收标准”中，要在规划阶段写成可执行的用例：

~~~text
AC01 通用Chat默认入口
前置：用户已登录客户端
操作：点击“新建Chat”
期望：直接进入通用助手，不强制选择角色
证据：真实客户端录屏或PNG
对应需求：R03

AC02 未授权目录不可读
前置：仅授权资料目录A
操作：要求Agent读取目录B的文件
期望：读取被拒绝或弹出真实授权请求
证据：操作日志 + 权限弹窗截图
对应需求：R08
~~~

要先看用例能不能表达用户想要的产品形态，再进入技术拆分。

## 7. S2：先画产品草图，再写架构

用户要知道“最终呈现什么”时，先给 ASCII 草图：

~~~text
┌──────────────┬────────────────────────────┬───────────────┐
│ 新建Chat      │ 对话与分析结果             │ 任务与资料状态 │
│ 通用助手      │                            │               │
│ 专家中心      │ 来源、指标、风险、待确认项 │ 当前Skill      │
│ 历史任务      │                            │ 授权状态       │
├──────────────┴────────────────────────────┴───────────────┤
│ 文件 / 语音 / 输入问题                         停止 发送  │
└───────────────────────────────────────────────────────────┘
~~~

草图确认的是：

- 页面结构。
- 用户入口。
- 信息层级。
- 角色位置。
- 文件和权限如何让用户感知。

草图未确认前，不应投入复杂 UI 编码。

## 8. S3：架构只讲必要概念

本案例最简架构：

~~~text
React Renderer
→ Electron安全IPC
→ Electron主进程
→ codex app-server子进程
→ 国内Model Gateway
→ 模型
~~~

对产品评审只需解释：

- 页面由自己设计。
- 主进程启动内置 Codex CLI。
- App Server 是 Codex CLI 自带的程序化入口，不是另一套产品。
- 用户看不到 CLI 和 Key。
- 真实文件操作受沙盒控制。

不需要在产品方案中展开每个 Service、类名和协议字段。

## 9. S4：可信 Agent 的四条硬线

银行类 Agent 的核心不是“回答得像”，而是“回答可验证”。

### 9.1 来源可信

- 指定资料优先。
- 回答标明文件、章节、字段和时间。
- 无依据时明确说不知道。
- 冲突资料同时列出，不擅自选择。

### 9.2 计算可信

- 写明单位。
- 写明公式。
- 写明来源列。
- 确定性计算尽量交给代码或受控 Tool。
- 大模型负责解释，不负责随意编造数值。

### 9.3 权限可信

- 用户选择目录。
- Skill 不扩大权限。
- 角色不扩大权限。
- Tool 每次执行二次校验。
- 审批弹窗与底层真实权限一致。

### 9.4 Key 可信

- 上游真实 Key 只在网关服务端。
- 客户端只接触短期凭证。
- Key 不进入页面、日志、命令行和安装包。
- 不把“输入框隐藏”误认为安全。

## 10. S5：开源项目借鉴必须回答四个问题

每个参考项目都要说明：

1. 借鉴哪里。
2. 为什么适合。
3. 是直接复用、选择性抽取还是只借鉴。
4. 需要删除或调整什么。

示例：

| 来源 | 借鉴部分 | 方式 | 调整 |
|---|---|---|---|
| Codex CLI | Thread、Turn、流式、停止、审批、沙盒 | 直接复用 | 隐藏终端和技术配置 |
| WorkBuddy | 专家中心、角色卡片、主动选择 | 产品借鉴 | 不绑定岗位，不做专家团 |
| 稳卖/Polaris | Electron 外壳、Chat、文件选择、任务状态 | 选择性抽取 | 删除 ACP、多 Backend、自配 Key |
| Gundam Agent | Chat 布局与状态反馈 | 设计借鉴 | 不复用第二套 Agent 主循环 |
| PCB Agent | 运行、等待授权、完成、失败状态 | 状态借鉴 | 删除 PCB 业务 |
| 开源金融 Skill | 分析流程和通用公式 | 方法改造 | 替换欧美口径和投资建议 |

任何代码复用前检查：

- 来源 commit。
- LICENSE。
- NOTICE。
- 网络访问。
- 文件写入。
- 依赖安全。
- 是否适合中国金融语境。

## 11. S6：仓库基线先于开发

### 必查项

~~~text
远端仓库：
本地路径：
当前分支：
main是否有首个commit：
目标worktree：
AGENTS.md：
CLAUDE.md：
未提交改动：
已有服务：
~~~

### 本案例教训

最初 clone 时远端是空仓库，后来远端已经出现十个 PR。如果只依赖旧本地状态，就会错误判断：

- 远端仍为空。
- 当前没有 PR。
- 总共预计只有五个 PR。

正确做法：

- 本地状态和远端状态分开检查。
- 汇报 PR 数量前使用 GitHub 实际数据。
- 不把昨天的审计结果当今天的事实。
- 方案文档中的“当前状态”必须带日期。

## 12. S7：总体计划应该包含什么

总体计划至少包含：

1. 用户原始需求及 Rxx 编号。
2. 产品结论。
3. 用户旅程。
4. 页面草图。
5. 验收测试用例及 ACxx 编号。
6. Rxx ↔ ACxx 双向对照表。
7. Role、Skill、Tool 定义。
8. Codex CLI 接入概念。
9. 沙盒、Key 和联网边界。

12. 任务依赖图。
13. 风险和延期项。
14. 当前仓库基线。

总体计划是“全局地图”，不应该直接承担每名员工的执行细节。

## 13. 本案例：我是怎么一步步拆出任务的

前面是方法，这一节是 Finance Agent 的实际拆分过程。拆分不是从技术模块名开始，而是从“你说了什么”和“你最后怎么验收”之间倒推。

### 第一步：保留用户原话，不急着拆技术

先从对话中提取用户已明确的结论：

| 需求编号 | 用户意图 |
|---|---|
| R01 | 要做一个自己的 C/S 桌面客户端，不是给用户看 CLI |
| R02 | 内部能力直接使用 Codex CLI，不自研第二套 Agent Runtime |
| R03 | 新建 Chat 默认就是通用助手，不强制先选角色 |
| R04 | 另有类 WorkBuddy 的专家中心，角色由用户主动选择 |
| R05 | MVP 只看 Agent + Skill 能不能真正跑起来，先不做 PPT、OCR、付费 |
| R06 | 用户不需要自己填 Key，也不需要翻墙 |
| R07 | 银行回答要可信，应限定资料范围、给出来源、不知道时明说 |
| R08 | 客户端可以读用户授权的本地文件，但不能等于取消沙盒 |

这一步只确认产品意图，不先写 `Service` 或协议字段。

### 第二步：把需求改写成用户可操作的验收用例

| 验收用例 | 用户实际操作与期望结果 | 对应需求 |
|---|---|---|
| AC01 | 启动真实 Mac 客户端，能看到自己的 Agent 页面 | R01 |
| AC02 | 点击新建 Chat，不选角色就能发起对话 | R03 |
| AC03 | 回答能流式输出、停止和继续追问 | R02、R03 |
| AC04 | 进入专家中心，可主动选择三个专家 | R04 |
| AC05 | 同一份资料在不同专家下展现不同 Skill 的处理方式 | R04、R05 |
| AC06 | 选择资料目录后，回答带文件或字段来源 | R07、R08 |
| AC07 | 要求读取未授权目录时被拒绝或请求授权 | R08 |
| AC08 | 用户界面不出现上游 Key，国内网络可完成真实对话 | R06 |
| AC09 | 退出客户端后，内置 Codex 进程正常结束 | R01、R02 |

到这里，产品的“100”已经可观察。后面所有任务都要为这些用例服务。

### 第三步：从验收用例倒推“必须存在的能力”

| 用例组 | 为了通过用例，必须存在的能力 |
|---|---|
| AC01、AC09 | Electron 外壳、启动/退出、子进程生命周期 |
| AC02、AC03 | Chat 页面、Thread/Turn、流式事件、停止与追问 |
| AC04、AC05 | 专家中心、角色定义、Skill 加载与可见状态 |
| AC06、AC07 | 文件选择、工作区授权、沙盒、引用输出 |
| AC08 | 国内 Model Gateway、客户端凭据、Key 脱敏 |

这一步才开始谈技术，而且只列通过用例必需的能力。

### 第四步：先拆“能不能走通”的 PoC，不急着做完整页面

最大技术不确定性不是按钮长什么样，而是两条链路能否成立：

~~~text
PoC-A：Electron是否能启动内置 codex app-server
→ 建立Thread
→ 发起Turn
→ 收到流式事件
→ 停止
→ 正常退出

PoC-B：国内Model Gateway是否可用
→ 客户端不放真实上游Key
→ 国内网络请求
→ 真实返回模型结果
~~~

因此最先拆出 `T01 App Server PoC` 和 `T02 Model Gateway PoC`。两个 PoC 不通，后面的页面和角色都只是空壳。

### 第五步：按可独立验收的产品切片拆任务

| 任务 | 任务目标 | 来源需求 | 主要验收用例 |
|---|---|---|---|
| T01 | 证明 Codex App Server 链路真实可调用 | R02 | AC03、AC09 |
| T02 | 证明国内网关和无感 Key 链路成立 | R06 | AC08 |
| T10 | 搭建可真实启动的 Electron 客户端骨架 | R01 | AC01、AC09 |
| T11 | 把 Codex 子进程生命周期接入主进程 | R01、R02 | AC03、AC09 |
| T12 | 把 Chat 操作转成 Thread/Turn 并展示流式结果 | R02、R03 | AC02、AC03 |
| T20 | 完成通用 Chat 和独立专家中心的产品入口 | R03、R04 | AC02、AC04 |
| T21 | 实现制度资料问答 Skill | R04、R05、R07 | AC05、AC06 |
| T22 | 实现企业经营数据分析 Skill | R04、R05、R07 | AC05、AC06 |
| T23 | 实现授信材料预审 Skill | R04、R05、R07 | AC05、AC06 |
| T30 | 接入授权目录、沙盒和引用证据 | R07、R08 | AC06、AC07 |
| T40 | 将所有已验证切片接到同一条用户旅程 | 全部 MVP 需求 | AC01–AC09 |
| T41 | 按墨刀调整真实客户端 UI，不改 Runtime | R01、R03、R04 | 界面类用例 |
| T42 | 做最终安全、凭据、依赖和端到端审计 | 全部 MVP 需求 | AC01–AC09 |

任务是按“可观察结果”拆的，不是为了让每个技术名词都有一张单。

### 第六步：画依赖，决定哪些可并行

~~~text
T01 App Server PoC ─┐
                     ├→ T11 Runtime → T12 Chat桥接 ─┐
T10 Electron骨架 ──┘                              │
                                                    ├→ T40集成 → T41 UI → T42最终验收
T02 Gateway PoC → 无感Key链路 ──────────┐         │
T20 专家中心 → T21/T22/T23 Skills ─────├─────────┘
T30 目录权限与引用 ─────────────────┘
~~~

并行的前提不是“有空闲 CLI”，而是：

- 前置依赖已通过。
- 文件范围不冲突。
- 每张任务都有自己的 ACxx。
- 单独完成后可以提供证据。

### 第七步：再把任务装进最多三个 CLI

不是一次把所有 CLI 启动，而是分波次：

| 波次 | CLI 1 | CLI 2 | CLI 3 | 主监工闸门 |
|---|---|---|---|---|
| Wave 1 | T01 App Server PoC | T02 Gateway PoC | 只读仓库/安全审计 | 两条链路未真实通过前，不进入全量开发 |
| Wave 2 | T10/T11 客户端与 Runtime | T20 专家中心 | T30 目录权限 | 文件边界不重叠，主监工逐项 Review |
| Wave 3 | T12 Chat 桥接 | T21–T23 Skills | 只读测试 Review | AC02–AC07 逐项出证据 |
| Wave 4 | T40 集成 | T41 UI（唯一 UI 写员工） | T42 审计 | 在同一最终组合树里跑 AC01–AC09 |

实际调度中，同一时刻不超过三个 CLI；如果两个任务会修改同一入口文件或全局样式，就改为顺序执行。

### 第八步：用户纠偏后，从锚点重新计算，不只改当前页面

本案例中出现过的纠偏：

| 用户纠偏 | 需求/用例变化 | 拆分如何跟着变 |
|---|---|---|
| “新建 Chat 就直接用 Codex，角色去单独页面选” | 更新 R03/R04、AC02/AC04 | 从“先选角色”改为“通用 Chat + 专家中心” |
| “只要 MVP，PPT 都不用做” | 更新 R05，删除 PPT 验收用例 | PPT/OCR/付费任务整体移出当前任务图 |
| “我只要 1 和 100 两头” | 需求方案改为产品形态 + 验收结果 | Service/Adapter 细节下沉到任务 MD，不再占总体方案主体 |
| “我要的是自己做 Agent 页” | 更新 R01、AC01 | 放弃直接套官方客户端，拆出 Electron 壳和自有 UI |
| “我做客户端，本地文件当然要能读” | 更新 R08、AC06/AC07 | 同时保留本地文件能力和沙盒越界测试 |

这才是完整的拆分逻辑：

~~~text
用户需求 Rxx
→ 用户确认的验收用例 ACxx
→ 通过用例必需的最小能力
→ 消除最大不确定性的 PoC
→ 可独立验收的任务 Txx
→ 依赖图和文件边界
→ 最多三个 CLI 分波执行
→ 统一集成后再跑 ACxx
→ 用户发现偏差并引导下一轮
~~~

## 14. S8：把总体计划拆成任务 MD

### 拆分原则

一个任务只解决一个可以独立验收的问题。

好的拆分：

~~~text
T01 App Server PoC
T02 Model Gateway PoC
T10 Electron骨架
T11 Runtime
T12 Chat桥接
T20 专家中心
T21/T22/T23 三个Skills
T30 登录与Key安全
T40 端到端集成
T42 最终审计
~~~

不好的拆分：

> 做完整个金融 Agent。

### 每张任务 MD 模板

~~~markdown
# Txx：任务名称

## 员工身份

## 对应需求 Rxx

## 对应验收用例 ACxx

## 前置依赖

## 目标

## 允许修改文件

## 禁止修改文件

## 实施步骤

## 必须测试

## 截图或证据

## 完成标准

## 风险边界

## 交付格式
~~~

### 文件边界规则

- 不写“允许修改整个仓库”。
- 多员工不得同时修改同一文件。
- 全局样式、入口文件和共享契约尽量由一个员工顺序处理。
- 设计审计员工可以只读，不需要 worktree。
- UI 大改通常一个写员工比三个并发更安全。

## 15. S9：主监工与 CLI 员工的职责

### Codex 主监工

- 读取总体计划。
- 创建任务包。
- 建立状态看板。
- 分配任务。
- 控制并发。
- 持续读取输出。
- Review diff。
- 运行测试。
- 处理集成。
- 真实启动产品。
- 最终统一汇报。

### Claude Code CLI 员工

- 一次只执行一张任务单。
- 只修改允许文件。
- 不扩大架构。
- 不启动其他 Agent 或 CLI。
- 不自行 push、PR、merge 或部署。
- 提交测试证据和风险。

### 并发规则

- 全项目最多三个 CLI。
- UI 改造建议最多两个 CLI。
- 只有一个 UI 写员工。
- 其他员工可以做只读设计审计或测试 Review。
- 不为凑并发提前启动未满足依赖的任务。

## 16. S10：状态看板和监督循环

任务状态只使用：

~~~text
pending
running
review
fix
blocked
done
deferred
~~~

标准监督循环：

~~~text
派发任务
→ 记录对应Rxx和ACxx
→ 记录员工、worktree、文件范围和验收标准
→ 检查并发和资源
→ 启动CLI
→ 持续读取输出
→ 员工完成
→ 主监工Review
→ 主监工按ACxx运行测试
→ 失败则带证据退回
→ 修复后重新Review
→ 标记done
→ 检查下游依赖
~~~

主监工不能：

- 只启动 CLI 后离开。
- 不看 diff 就接受完成。
- 用员工口头报告代替测试。
- 把十个独立 PR 当成已经集成的产品。

## 17. S11：PR 不是越多越好

### 什么时候一任务一 PR

- 文件范围独立。
- 依赖清晰。
- 单独合并仍能构建。
- Review 价值明确。

### 什么时候应该一个集成 PR

- 多任务修改同一入口或全局样式。
- 堆叠 PR 会重复大量文件。
- 单个 PR 合并后产品不可运行。
- 视觉任务必须形成完整页面闭环。

### 堆叠 PR 风险

本案例中 UI 与 Runtime 两条链都修改测试配置，临时集成时出现 `vitest.config.ts` 冲突。

正确做法：

- 合并前先构造最终组合树。
- 运行完整测试和构建。
- 发现冲突先解决并复测。
- 更新 PR 分支需要单独 push 授权。
- 不使用 rebase。
- 每次目标分支变化后重新计算最终 diff。

## 18. S12：UI 参考图如何真正落地

### 设计输入

可以是：

- 墨刀。
- Figma。
- 图片。
- 已上线页面。

### 标准流程

~~~text
打开设计原型
→ 识别页面和交互
→ 提取尺寸、颜色、字体、间距
→ 保存设计截图
→ 启动当前客户端
→ 保存基线截图
→ 建立差异表
→ 实现真实组件
→ 启动Electron
→ 同尺寸截图
→ 逐项对比
→ 修正
~~~

### 1:1 的正确含义

- 使用真实 React/Vue 组件。
- 文本可选中。
- 按钮可交互。
- 布局可响应。
- 状态可测试。
- PNG 来自真实运行窗口。

不允许：

- AI 生成一张看起来相似的效果图。
- 把设计稿整图放进页面。
- 只在浏览器打开 HTML，不验证 Electron。
- 只看代码，不看运行结果。

## 19. S13：最终验收分层

### 层 1：单任务验收

- 目标完成。
- 文件范围正确。
- 单测通过。
- 无中高风险。

### 层 2：模块验收

- UI、Runtime、Skills 分别可用。
- 接口契约一致。
- 不依赖员工机器的临时状态。

### 层 3：端到端验收

~~~text
启动客户端
→ 登录
→ 新建Chat
→ 调用真实网关
→ 流式回答
→ 停止
→ 继续追问
→ 选择专家
→ 读取授权资料
→ 返回带来源答案
→ 退出无残留进程
~~~

### 层 4：用户验收

- 用户按自己确认的 ACxx 逐条验收，而不是按开发者自证。
- 用户拿到启动命令或安装包。
- 用户按步骤可以复现。
- 截图与实际页面一致。
- 未完成事项明确标记。
- Mac 完成不能写成 Windows 已完成。

## 20. 必做风险门禁

合并、提交或交付前检查：

### 凭据

- Key、Token、Cookie、Authorization。
- `.env` 和本地配置。
- 日志、命令行和截图。

### 权限

- 沙盒是否退化。
- Renderer 是否获得 Node 权限。
- 路径是否可以越界。
- 角色或 Skill 是否增加权限。

### 网络

- 是否开放任意公网。
- 是否存在跨域凭据转发。
- 是否使用域名白名单。
- 超时、重试和错误是否可信。

### Git

- 是否混入 node_modules、dist、target、日志和截图。
- 是否混入其他员工改动。
- PR 文件范围是否与计划一致。
- 合并后的最终树是否重新测试。

中高风险未清零，不得继续交付。

## 21. 常见误区与纠偏

| 误区 | 后果 | 纠偏 |
|---|---|---|
| 一开始展开中间黑盒 | 用户不知道最终产品是什么 | 先讲用户界面、旅程和结果 |
| 把 App Server 说成另一个产品 | 造成“是否需要 App Store”的误解 | 明确它是 Codex CLI 自带模式 |
| 桌面客户端不需要沙盒 | 本地文件无边界 | 客户端与沙盒分别解决入口和边界 |
| 用 Skill 代替权限控制 | Prompt 可被绕过 | Skill 管方法，Tool/Runtime 管权限 |
| 角色与岗位绑定 | 产品僵化且产生误权限 | 角色由用户主动选择，不增加权限 |
| 开源项目全量 fork | 带入多 Runtime、多 Provider 和债务 | 写清直接复用、抽取、借鉴 |
| PR 多等于进度快 | 分支堆叠、集成失败 | 看 main、集成树和端到端证据 |
| 本地旧状态当远端事实 | PR 数和仓库状态判断错误 | 每次状态问题实时查远端 |
| UI 用效果图验收 | 实际页面不一致 | 真实 Electron 窗口截图 |
| 多 CLI 同改全局样式 | 高频冲突 | UI 只保留一个写员工 |
| Key 曾经提供过就能再次拿到 | 凭据泄露或误用过期 Key | 短期注入、不落盘、重新发放 |

## 25. 一页式执行检查表

### 需求

- [ ] 用户的需求描述已原样保留并编号。
- [ ] 能用一句话说清产品。
- [ ] 能画出用户最终页面。
- [ ] 默认入口和角色入口明确。
- [ ] MVP 和以后做的内容已分开。
- [ ] 每条核心需求都有对应验收用例。
- [ ] 验收用例能表达用户最终看到的产品形态。

### Skill 路由

- [ ] 重复出现的长 Prompt 和纠偏流程已评估是否沉淀为 Skill。
- [ ] 每个 Skill 的描述都写清“何时用”和“何时不用”。
- [ ] Skill 已按任务域分层，没有把大量 Skill 无差别平铺。
- [ ] 路由使用先召回、再重排、只加载少量命中 Skill 的方式。
- [ ] 已覆盖正命中、误命中、漏命中和模糊输入测试。
- [ ] Skill 命中不会扩大 Tool、文件、网络或沙盒权限。

### 技术

- [ ] 直接复用与只借鉴已区分。
- [ ] Agent Runtime 只有一套。
- [ ] Key、网络、文件和沙盒边界明确。
- [ ] PoC 闸门明确。

### 仓库

- [ ] 远端和本地状态实时核验。
- [ ] 分支、worktree 和 Git 权限明确。
- [ ] 无关 diff 和敏感文件已隔离。

- [ ] 总体计划已拆成小任务 MD。
- [ ] 每张任务有文件范围和测试。
- [ ] 依赖图和状态看板存在。

### 集成

- [ ] PR 顺序明确。
- [ ] 堆叠冲突已提前验证。
- [ ] 最终组合树通过测试。
- [ ] 中高风险清零。

### 验收

- [ ] 使用真实模型链路。

- [ ] 使用真实客户端窗口。

- [ ] 延期项没有伪装成通过。

## 26. SOP 的核心原则

最后只记住九句话：

1. 始终盯住两个锚点：用户的需求描述和用户确认的验收测试用例。
2. 用户通过需求和用例持续纠偏，AI 必须把纠偏回写到计划与任务。
3. 先讲用户得到什么，再讲技术怎么绕。
4. 先砍出 MVP，再谈完整平台。
5. Skill 管方法，Tool 和 Runtime 管权限。
6. 总体计划管全局，任务 MD 管执行，Rxx 和 ACxx 管方向。
7. PR 不是完成，通过验收用例的端到端真实运行才是完成。
8. UI 效果图不是验收，满足用例的真实客户端才是验收对象。
9. Prompt 只表达本次意图，Skill 沉淀可复用方法，AI 自动路由，用户仍只盯 Rxx 和 ACxx。
